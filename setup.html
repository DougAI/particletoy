particletoy — setup guide

From local dev to a fully hosted community site with accounts, likes, comments and curation.

Works with zero setup: the editor, both PBR pipelines, URL sharing, browser library, JSON export/import.

Needs ~10 minutes of setup: the community site — accounts, publishing, the gallery, likes, comments, notifications, avatars. It runs on a free Supabase project (steps 3–4).

1Run it locally

particletoy is a fully static app (plain ES modules, zero dependencies, no build step), but browsers refuse ES modules from file:// — serve the folder:

cd C:\projects\particletoy
python serve.py            # then open http://localhost:8917

Any static server works, but on Windows avoid plain python -m http.server — it can serve .js as text/plain (registry MIME types), which breaks ES modules. Requirements: WebGPU (current Chrome / Edge / Safari / Firefox).

Page map

index.htmlfront page — particle of the day, featured, latest

view.html?id=…a particle's page — player, likes, comments

2Host the static site (GitHub Pages)

Everything is static, so hosting is "upload the folder". With the repo already on GitHub: repo → Settings → Pages → Source “Deploy from a branch” → branch master, folder / (root) → Save. The site appears at https://<you>.github.io/particletoy/. Netlify / Cloudflare Pages work identically (build command: none, publish dir: /).

3Create the backend (Supabase)

The community features use Supabase — Postgres + auth + file storage behind a REST API, called directly from the browser with no SDK. The free tier is plenty.

  1. Create a project at supabase.com/dashboard (any name/region; note the database password somewhere safe).
  2. Dashboard → SQL Editor → New query: paste the entire contents of supabase/schema.sql from this repo and Run. It creates every table, security policy, trigger and the storage bucket. Re-running it later is safe.
  3. Project Settings → API: copy the Project URL and the anon / publishable key into the two constants at the top of js/backend.js. (Already done if the constants are filled in.)

The publishable key is designed to be public — row-level security policies in the schema are what limit what visitors can do. Private particles are enforced by the database, not the client.

4Configure authentication

In the Supabase dashboard:

  1. Authentication → Sign In / Providers → Email: make sure Email is enabled (it is by default).
  2. Decide on email confirmation:
    • Frictionless (recommended to start): turn off “Confirm email”. Sign-ups work instantly and no mail is sent.
    • Verified: leave it on — users must click a link before signing in. Do not ship this on the built-in SMTP: it allows only a few messages per hour project-wide, so you will hit email rate limit exceeded almost immediately — during your own testing, let alone with real users. Confirmation is only practical with custom SMTP (Authentication → Emails → SMTP settings) via Resend / Postmark / SES.

    Gotcha when switching this off later: accounts created while confirmation was on stay unconfirmed and still can't sign in — the setting only affects new sign-ups. Delete or confirm those rows under Authentication → Users. The same applies to password-reset and email-change mail, which always sends regardless of this toggle.

  3. Authentication → URL Configuration:
    • Site URL: your hosted URL, e.g. https://<you>.github.io/particletoy/
    • Redirect URLs: add http://localhost:8917/* (dev) and https://<you>.github.io/particletoy/*
    Password-reset and email-change links land on account.html, which handles them automatically.

5Make yourself admin & curate the front page

Sign up through the site first, then in the SQL editor:

update public.profiles set is_admin = true where username = 'your_username';

Admins see two extra buttons on every particle page — ★ Feature (adds it to the front-page featured grid) and ☀ POTD (makes it the particle of the day). Until anything is curated, the front page falls back to the most-loved particles automatically, so the site never looks empty.

6Link previews (Discord, Slack, Twitter)

Optional, and the one part that needs more than static files. Paste a particle link into Discord and you want a card with the title, the author and the effect playing — not a bare URL.

The obstacle: link crawlers don't run JavaScript, and this site is static. A crawler asking GitHub Pages for view.html?id=… gets the same <head> no matter which particle you linked, so the card can't be built in the browser. Something has to answer that URL with per-particle <meta> tags. That something is og/index.js, which looks the particle up as anon (so private ones stay private), renders the tags, and redirects real browsers to the actual page.

It cannot run on a *.supabase.co/functions/v1/ URL. Supabase rewrites an edge function's text/html GET response to text/plain, on purpose, so its domain can't serve web pages. The tags arrive perfectly intact and every crawler ignores them, because nothing parses meta tags out of plain text.

The symptom is a link that previews as nothing at all, from a function that looks completely healthy in curl — 200, right body, right title. The giveaway is in the response headers: Content-Type: text/plain next to Content-Security-Policy: default-src 'none'; sandbox. Don't try to dodge it by mislabelling the response; it is an anti-phishing control.

So host it somewhere that serves HTML. og/index.js is plain JavaScript with no dependencies and no build step, and detects its runtime, so the same file runs on all of the options below — paste it in, set two environment variables, done.

Cloudflare Workers (free, has a paste-in editor)

  1. dash.cloudflare.com → Workers & Pages → Create → Start with Hello World → deploy it, then Edit code.
  2. Replace the contents with og/index.js and deploy. You get https://<name>.<subdomain>.workers.dev.
  3. Nothing to configure. The project URL and publishable key are constants at the top of the file, exactly as they are in js/backend.js and public for the same reason — the endpoint reads as anon, so row-level security is what limits it. Change them there for your own project, or override with SUPABASE_URL / PT_ANON_KEY / SITE_URL under Settings → Variables and Secrets if you would rather not edit the file.
  4. Point the app at it. In js/backend.js: 
    const SHARE_BASE = 'https://<name>.<subdomain>.workers.dev/og';
    There is no default, deliberately — until this is set, Share hands out the plain page link, which still previews, just with the site card rather than the particle's own.
  5. Re-run schema.sql if your project predates this feature. It adds the preview_* columns and widens the media bucket to accept video (it is safe to re-run).

Alternatives. Deno Deploy runs the same file (it picks up the Deno.serve at the bottom instead of the default export); note that Deploy Classic and its playground were retired in July 2026, so use console.deno.com. Or stay on Supabase with the Pro plan plus the Edge Functions custom domain add-on, which lifts the HTML restriction — copy the file to supabase/functions/og/index.js, deploy with supabase functions deploy og --no-verify-jwt, and keep Verify JWT off, since a crawler cannot send an API key and would otherwise get a 401.

?debug=1 reports configFrom, saying whether each value came from an environment variable or the built-in constant — worth checking first when a card is wrong and the host's dashboard claims otherwise.

If the storage.buckets statement in schema.sql errors on your project, set it by hand instead: Storage → media → Settings → file size limit 8 MB, allowed MIME types image/jpeg, image/png, image/webp, image/gif, video/mp4, video/webm.

The function is not part of the static site. Pushing to the branch GitHub Pages serves updates the pages, and nothing else — the edge function keeps running the code you last deployed until you run supabase functions deploy og again. Worth remembering when a fix to index.ts appears to have changed nothing.

Checking it

?debug=1 answers "why is my card wrong" in one request — whether the particle was found, what the database said, and what the card will show:

curl 'https://<your-og-host>/og/<particle-id>?debug=1'
  • Anything but JSON (an error page, "Function not found") — the function isn't deployed under the name og.
  • {"code":401} — on Supabase, Verify JWT is still on.
  • "note": "not configured: …" — an environment variable is set to an empty value, overriding the built-in constant with nothing.
  • Correct-looking HTML that still previews as nothing — check the Content-Type. If it says text/plain, the host is neutering the page (see the box above).
  • particleFound: false with restStatus: 200 — the particle is private, or the id is wrong. Previews read the database as anon, exactly like a signed-out visitor.
  • restStatus: 401 — the anon key didn't work; set PT_ANON_KEY (below).
  • cardWouldShow tells you whether the card plays a clip, shows a still, or falls back to the generic image.

?card=1 renders the actual HTML, so you can read the tags:

curl -i 'https://<your-og-host>/og/<particle-id>?card=1'

Check the headers as well as the body: a Content-Type of anything but text/html means the host is refusing to serve it as a page, and no crawler will read the tags however correct they are.

Discord caches an embed per URL for a good while, including the "no embed" result. After a fix, test with a cache-busting query (…/og/<id>?v=2) rather than the URL that already failed.

What gets shared. Publishing captures a still thumbnail and a ~3-second clip (H.264 where the browser can encode it, WebM otherwise, GIF as a last resort), stored in the media bucket. Discord and Twitter play a direct MP4 given to them as og:video; anything that won't shows the thumbnail instead, so the card is never empty. Particles published before this existed can get a clip from the Link preview → Render clip button on their own page, without a trip to the editor. The clip matters everywhere except X, which runs the effect live for every particle either way (see below) — worth rendering for Discord and for the still that LinkedIn and Bluesky show, but no longer the difference between a card and a dead one.

Video or GIF. The Link preview box has a format picker, and Video is the compatible choice. It stores an MP4 for og:video, which Discord and Twitter play inline, and leaves the 1200×630 still as the og:image that every other platform uses. GIF instead becomes the og:image itself: it animates on Slack and Telegram, shows as a first frame on Discord, and is too small for LinkedIn, which passes over it and takes the still offered behind it. Switching format re-renders the clip, replaces the stored one, and refreshes the still.

X is the one that renders the effect itself: it iframes whatever twitter:player points at, which is embed.html?id=… — the player with no site chrome around it. (Point that at view.html and the card shows the entire website, header and search box and all, squeezed into a 16:9 box.) The plain ?id= URL is the page's decorative mode, and the card wants exactly that: no anchors anywhere in the document, so the frame has nowhere to navigate to, and no pointer events, so a drag or a scroll over the card goes to the timeline instead of the orbit camera. Every particle gets it, clip or no clip: there is nothing to pre-render, because the embed runs the effect in the reader's own browser. A stored clip is still handed over as twitter:player:stream, and the thumbnail is still the twitter:image X shows while the iframe loads — so a particle that has neither previews no worse than it did before. Everywhere else the clip is as close as it gets: embeds are limited to each platform's own list of providers. LinkedIn also caches hard — use its Post Inspector to force a re-fetch rather than assuming a fix didn't work.

The Share button hands out the function's URL, because that is the address a crawler has to fetch for any of this to happen — clicking it lands on the normal page. The card names that same URL in og:url, which looks wrong until you meet LinkedIn: it treats og:url as the identity of what is being shared and rebuilds the card from whatever is at it, so pointing it at view.html sent LinkedIn to a static file with generic tags and no ?id — every particle filed under one URL, one generic card, which reads as no preview at all. Keep og:url self-referential in any fork. Editor Share links (#s=…) can never preview: the effect rides in the URL fragment, which browsers never send to a server. Discord won't run the live player either — it only iframes a handful of whitelisted providers, so there a playing clip is as close as it gets.

To put a particle in your own page, iframe the same page — Share → Embed on your own page has the snippet ready to copy: <iframe src="https://<you>.github.io/particletoy/embed.html?id=<particle-id>&interactive=1" width="640" height="360" allowfullscreen></iframe>. The interactive flag is the difference from the card: it turns on orbit, zoom, the controls and a credit linking back — an embed you placed yourself is one you want people to touch, so it may keep the wheel. It plays live where WebGPU is available and falls back to the particle's clip or still where it isn't. Keep the iframe at the same ratio as the canvas (16:9) or you get letterboxing.

Moving it later is one constant: point SHARE_BASE in js/backend.js at whatever answers <base>/<particle-id> with these tags. Links already shared keep working only if the old host stays up, so prefer a home you will keep.

7Donate buttons

The front page shows PayPal and Patreon buttons. Point them at your real pages in js/site.js:

export const LINKS = {
  paypal:  'https://www.paypal.com/donate/?hosted_button_id=XXXXXXXX',
  patreon: 'https://www.patreon.com/yourpage',
  github:  'https://github.com/you/particletoy',
};

PayPal: paypal.com → Pay & Get Paid → Donate button → create, copy the hosted button id. Patreon: your creator page URL.

8How the pieces fit

Browser (static pages on GitHub Pages)
  │  fetch() — plain REST, no SDK
  ▼
Supabase
  ├─ Auth (GoTrue)     sign-up/in, password reset, email change → JWT
  ├─ PostgREST         /rest/v1/* — tables below, guarded by RLS + the JWT
  │    profiles        username, display name, avatar, bio, notify prefs
  │    particles       title, description, tags[], data (jsonb), visibility,
  │                    views/likes/comment_count (trigger-maintained)
  │    likes, comments counters + in-app notifications via triggers
  │    featured        POTD + featured grid (admin-only writes)
  ├─ Storage           /media/<uid>/avatar.jpg, /media/<uid>/thumbs/<id>.jpg,
  │                    /media/<uid>/previews/<id>.mp4
  └─ (storage is also where preview clips live)

og/index.js on Cloudflare Workers / Deno Deploy
     <base>/<particle-id> — Open Graph tags for link crawlers,
     redirects humans to view.html. Reads Supabase as anon.
  • Clients can never write counters or is_admin — column-level grants.
  • Private particles are filtered by RLS in every query, including embeds.
  • View counts go through a bump_views() RPC; likes/comments maintain counters via triggers.
  • Card hover-previews and the POTD render the actual effect live in WebGPU — thumbnails are only the static fallback, captured on publish.

9Costs, limits, growth

  • Free tier: 500 MB database + 1 GB storage + 50k monthly active users — plenty for a hobby community. Effects are ~2–30 KB each.
  • If it takes off: Supabase Pro ($25/mo) removes the project-pausing-after-a-week of-inactivity behavior and raises limits.
  • Abuse controls worth adding later: Supabase Auth captcha (hCaptcha/Turnstile toggle in Auth settings), a reported flag on particles, and rate limiting via Supabase's built-ins.

Have fun. The ? button in the editor documents the full shader API (PBR Surface struct, particle inputs, noise library).
