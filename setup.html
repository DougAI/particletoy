particletoy — setup guide

From local dev to a fully hosted community site with accounts, likes, comments and curation.

Works with zero setup: the editor, both PBR pipelines, URL sharing, browser library, JSON export/import.

Needs ~10 minutes of setup: the community site — accounts, publishing, the gallery, likes, comments, notifications, avatars. It runs on a free Supabase project (steps 3–4).

1Run it locally

particletoy is a fully static app (plain ES modules, zero dependencies, no build step), but browsers refuse ES modules from file:// — serve the folder:

cd C:\projects\particletoy
python serve.py            # then open http://localhost:8917

Any static server works, but on Windows avoid plain python -m http.server — it can serve .js as text/plain (registry MIME types), which breaks ES modules. Requirements: WebGPU (current Chrome / Edge / Safari / Firefox).

Page map

index.htmlfront page — particle of the day, featured, latest
browse.htmlsearch / sort / tag browsing
view.html?id=…a particle's page — player, likes, comments
editor.htmlthe editor (old share links to index.html redirect here)
account.htmlyour particles, profile, settings
user.html?u=…anyone's public profile

2Host the static site (GitHub Pages)

Everything is static, so hosting is "upload the folder". With the repo already on GitHub: repo → Settings → Pages → Source “Deploy from a branch” → branch master, folder / (root) → Save. The site appears at https://<you>.github.io/particletoy/. Netlify / Cloudflare Pages work identically (build command: none, publish dir: /).

3Create the backend (Supabase)

The community features use Supabase — Postgres + auth + file storage behind a REST API, called directly from the browser with no SDK. The free tier is plenty.

  1. Create a project at supabase.com/dashboard (any name/region; note the database password somewhere safe).
  2. Dashboard → SQL Editor → New query: paste the entire contents of supabase/schema.sql from this repo and Run. It creates every table, security policy, trigger and the storage bucket. Re-running it later is safe.
  3. Project Settings → API: copy the Project URL and the anon / publishable key into the two constants at the top of js/backend.js. (Already done if the constants are filled in.)

The publishable key is designed to be public — row-level security policies in the schema are what limit what visitors can do. Private particles are enforced by the database, not the client.

4Configure authentication

In the Supabase dashboard:

  1. Authentication → Sign In / Providers → Email: make sure Email is enabled (it is by default).
  2. Decide on email confirmation:
    • Frictionless (recommended to start): turn off “Confirm email”. Sign-ups work instantly and no mail is sent.
    • Verified: leave it on — users must click a link before signing in. Do not ship this on the built-in SMTP: it allows only a few messages per hour project-wide, so you will hit email rate limit exceeded almost immediately — during your own testing, let alone with real users. Confirmation is only practical with custom SMTP (Authentication → Emails → SMTP settings) via Resend / Postmark / SES.

    Gotcha when switching this off later: accounts created while confirmation was on stay unconfirmed and still can't sign in — the setting only affects new sign-ups. Delete or confirm those rows under Authentication → Users. The same applies to password-reset and email-change mail, which always sends regardless of this toggle.

  3. Authentication → URL Configuration:
    • Site URL: your hosted URL, e.g. https://<you>.github.io/particletoy/
    • Redirect URLs: add http://localhost:8917/* (dev) and https://<you>.github.io/particletoy/*
    Password-reset and email-change links land on account.html, which handles them automatically.

5Make yourself admin & curate the front page

Sign up through the site first, then in the SQL editor:

update public.profiles set is_admin = true where username = 'your_username';

Admins see two extra buttons on every particle page — ★ Feature (adds it to the front-page featured grid) and ☀ POTD (makes it the particle of the day). Until anything is curated, the front page falls back to the most-loved particles automatically, so the site never looks empty.

6Link previews (Discord, Slack, Twitter)

Optional, and the one part that needs more than static files. Paste a particle link into Discord and you want a card with the title, the author and the effect playing — not a bare URL.

The obstacle: link crawlers don't run JavaScript, and this site is static. A crawler asking GitHub Pages for view.html?id=… gets the same <head> no matter which particle you linked, so the card can't be built in the browser. Something has to answer that URL with per-particle <meta> tags. That something is a small Supabase edge function — supabase/functions/og — which looks the particle up as anon (so private ones stay private), renders the tags, and redirects real browsers to the actual page.

  1. Deploy it. With the Supabase CLI: 
    supabase link --project-ref <your-project-ref>
supabase functions deploy og
    No CLI? Dashboard → Edge Functions → Deploy a new function → via Editor, name it og, paste supabase/functions/og/index.ts, and turn Verify JWT off.
  2. Verify JWT must be off. Discord can't send an API key, so with it on every crawler gets a 401 and no card. supabase/config.toml sets this for the CLI; the dashboard has a toggle on the function's settings.
  3. Point it at your site, if you host it anywhere but this repo's GitHub Pages URL: 
    supabase secrets set SITE_URL=https://example.com/particletoy
    It defaults to https://dougai.github.io/particletoy. The same URL is hard-coded in each page's og: tags for the generic site card — search the HTML files for og:image and change it there too.
  4. Re-run schema.sql if your project predates this feature. It adds the preview_* columns and widens the media bucket to accept video (it is safe to re-run).

Check a card without pretending to be a crawler by adding ?card=1:

curl 'https://<ref>.supabase.co/functions/v1/og/<particle-id>?card=1'

What gets shared. Publishing captures a still thumbnail and a ~3-second clip (H.264 where the browser can encode it, WebM otherwise, animated GIF as a last resort), stored in the media bucket. Discord and Twitter play a direct MP4 given to them as og:video; anything that won't shows the thumbnail instead, so the card is never empty. Particles published before this existed can get a clip from the Link preview → Render clip button on their own page, without a trip to the editor.

The Share button hands out the function's URL, because that is the address a crawler has to fetch for any of this to happen — clicking it lands on the normal page. Editor Share links (#s=…) can never preview: the effect rides in the URL fragment, which browsers never send to a server. Interactive embeds aren't possible either — Discord only runs players for a handful of whitelisted providers, so a playing clip is as close as it gets.

Prefer your own domain over <ref>.supabase.co/functions/v1/og/…? Anything that answers <base>/<particle-id> with the same tags works — a Cloudflare Worker or Netlify function wrapping the same code. Set SHARE_BASE in js/backend.js and the app hands out that address instead.

7Donate buttons

The front page shows PayPal and Patreon buttons. Point them at your real pages in js/site.js:

export const LINKS = {
  paypal:  'https://www.paypal.com/donate/?hosted_button_id=XXXXXXXX',
  patreon: 'https://www.patreon.com/yourpage',
  github:  'https://github.com/you/particletoy',
};

PayPal: paypal.com → Pay & Get Paid → Donate button → create, copy the hosted button id. Patreon: your creator page URL.

8How the pieces fit

Browser (static pages on GitHub Pages)
  │  fetch() — plain REST, no SDK
  ▼
Supabase
  ├─ Auth (GoTrue)     sign-up/in, password reset, email change → JWT
  ├─ PostgREST         /rest/v1/* — tables below, guarded by RLS + the JWT
  │    profiles        username, display name, avatar, bio, notify prefs
  │    particles       title, description, tags[], data (jsonb), visibility,
  │                    views/likes/comment_count (trigger-maintained)
  │    likes, comments counters + in-app notifications via triggers
  │    featured        POTD + featured grid (admin-only writes)
  ├─ Storage           /media/<uid>/avatar.jpg, /media/<uid>/thumbs/<id>.jpg,
  │                    /media/<uid>/previews/<id>.mp4
  └─ Edge function     /functions/v1/og/<id> — Open Graph tags for link
                       crawlers, redirects humans to view.html
  • Clients can never write counters or is_admin — column-level grants.
  • Private particles are filtered by RLS in every query, including embeds.
  • View counts go through a bump_views() RPC; likes/comments maintain counters via triggers.
  • Card hover-previews and the POTD render the actual effect live in WebGPU — thumbnails are only the static fallback, captured on publish.

9Costs, limits, growth

  • Free tier: 500 MB database + 1 GB storage + 50k monthly active users — plenty for a hobby community. Effects are ~2–30 KB each.
  • If it takes off: Supabase Pro ($25/mo) removes the project-pausing-after-a-week of-inactivity behavior and raises limits.
  • Abuse controls worth adding later: Supabase Auth captcha (hCaptcha/Turnstile toggle in Auth settings), a reported flag on particles, and rate limiting via Supabase's built-ins.

Have fun. The ? button in the editor documents the full shader API (PBR Surface struct, particle inputs, noise library).
